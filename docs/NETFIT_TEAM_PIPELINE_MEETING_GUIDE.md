# 1. 우리 서비스의 현재 구조

지금 NETFIT은 다음 순서로 동작한다.

```text
팀원이 GitHub의 runsv 브랜치에 코드를 올림
                    ↓
Render가 runsv 코드를 가져와 서버를 실행함
                    ↓
사용자가 NETFIT 웹사이트에 접속함
                    ↓
Django가 요청을 처리함
                    ↓
계정과 운동 기록은 Supabase DB에 저장됨
```

현재 운영 주소:

<https://netfit-production.onrender.com/>

## 현재 잘되는 것

- [x] Render에서 웹사이트가 열림
- [x] `runsv` 브랜치를 배포 대상으로 사용함
- [x] Django 서버가 실행됨
- [x] Supabase DB에 연결됨
- [x] 회원과 운동 기록을 DB에 저장함

- [x] 공공체육시설 CSV를 DB에 넣는 명령이 있음

## 아직 부족한 것

- [ ] 코드 오류를 자동 검사한 후 배포하는 기능

- [ ] 공공체육시설 데이터를 자동으로 새로 받는 기능
- [ ] 시설 데이터가 언제 갱신됐는지 기록하는 기능
- [ ] 정해진 시간마다 자동으로 데이터를 갱신하는 기능
- [ ] 실제 운영에 사용할 수 있는 크롤링 기능

# 2. 자주 나오는 용어를 쉽게 이해하기

| 용어 | 쉬운 의미 | NETFIT 예시 |
|---|---|---|
| 파이프라인 | 작업이 순서대로 이어지는 과정 | 코드 검사 → 배포 → 서버 실행 |
| CI | 코드에 문제가 없는지 자동 검사 | Django 검사와 테스트 실행 |
| CD | 검사에 합격한 코드를 자동 배포 | `runsv`를 Render에 반영 |
| Migration | Django 모델 변경을 실제 DB에 적용 | 새로운 컬럼과 테이블 생성 |
| ETL | 데이터를 정리한 뒤 DB에 저장 | CSV 정리 후 시설 테이블 저장 |
| ELT | 원본을 DB에 먼저 넣고 나중에 정리 | NETFIT에는 현재 필요성이 낮음 |
| Import | 이미 가지고 있는 파일을 DB에 넣음 | 현재 CSV 적재 작업 |
| Scraping | 웹페이지 하나에서 필요한 정보 추출 | 시설 홈페이지 운영시간 찾기 |
| Crawling | 여러 웹페이지를 돌아다니며 수집 | 여러 시설 홈페이지 순회 |
| Cron | 정해진 시간에 작업 자동 실행 | 매주 시설 데이터 갱신 |
| Health Check | 서버가 정상인지 확인 | `/healthz/` 요청 |

# 3. 지금 CSV를 넣는 작업은 크롤링인가?

## 결론

현재 작업은 크롤링이 아니다.

우리가 이미 받은 CSV 파일을 읽어 DB에 넣고 있기 때문에 다음 표현이 정확하다.

> 공공체육시설 CSV Import

또는

> 공공체육시설 ETL

현재 흐름:

```text
이미 다운로드한 CSV 파일
        ↓
시설 이름과 지역 확인
        ↓
일부 지역명 변경
        ↓
중복을 확인하며 DB에 저장
```

## 크롤링은 언제 사용하는가?

공식 CSV에 없는 정보가 꼭 필요할 때만 사용한다.

예시:

- 시설 운영시간
- 휴관일
- 예약 페이지
- 프로그램 안내
- 시설별 공지사항

우선순위는 다음과 같다.

```text
1순위: 공식 API
2순위: 공식 CSV 또는 JSON
3순위: 허용된 공식 홈페이지에서 정보 추출
4순위: 여러 사이트 크롤링
```

공식 데이터가 있으면 크롤링보다 공식 데이터를 먼저 사용한다. 웹페이지 구조는 자주 바뀌고 사이트에 부담을 줄 수 있기 때문이다.

# 4. NETFIT에는 ETL과 ELT 중 무엇이 맞는가?

## 팀 결론으로 권장하는 방식

NETFIT에는 **ETL 방식**이 더 적합하다.

```text
시설 데이터 받기
      ↓
잘못된 값 검사
      ↓
지역명과 좌표 정리
      ↓
중복 제거
      ↓
Supabase DB에 저장
```

## ETL을 추천하는 이유

- Supabase DB 용량을 아낄 수 있다.
- 잘못된 데이터를 DB에 넣기 전에 차단할 수 있다.
- 시설 데이터 크기가 아주 크지 않다.
- Django에서 데이터 검사를 구현하기 쉽다.
- 운영 화면에는 정리된 데이터만 보여줄 수 있다.

## 원본 CSV는 어디에 보관하는가?

선택지는 두 가지다.

### 간단한 방식

- 최신 CSV 한 개만 프로젝트 또는 별도 폴더에 보관
- 데이터가 변경되면 기존 파일 교체

### 권장 방식

- 원본 CSV는 Supabase Storage에 보관
- PostgreSQL DB에는 정리된 시설 정보만 저장
- 원본 이름, 수집 날짜, 버전을 DB에 기록

팀에서 결정할 질문:

- [ ] 원본 CSV를 GitHub에 계속 보관할 것인가?
- [ ] Supabase Storage에 보관할 것인가?
- [ ] 과거 버전을 몇 개까지 남길 것인가?

# 5. 현재 시설 데이터에서 고쳐야 할 부분

## 문제 1: 중복 기준이 약함

현재는 주로 시설 이름과 주소를 이용해 같은 시설인지 확인한다.

문제점:

- 시설 이름이 조금만 바뀌어도 새 시설로 저장될 수 있음
- 도로명주소가 변경되면 중복이 생길 수 있음

해결 방향:

1. 원본 데이터에 시설 고유번호가 있는지 확인한다.
2. 고유번호가 있으면 DB에 저장한다.
3. 같은 고유번호는 한 번만 저장하도록 DB 제약을 추가한다.

## 문제 2: 알 수 없는 지역을 서울로 저장함

현재 코드에는 인식할 수 없는 지역이 들어오면 서울로 저장될 가능성이 있다.

이렇게 되면 다른 지역 시설이 서울 시설로 잘못 표시될 수 있다.

해결 방향:

- 잘못된 지역은 저장하지 않고 오류 목록에 남긴다.
- 또는 `미분류`로 저장해 관리자가 확인한다.

## 문제 3: 언제 갱신했는지 알 수 없음

현재는 다음 정보를 충분히 남기지 않는다.

- 언제 실행했는지
- 몇 개를 새로 만들었는지
- 몇 개를 수정했는지
- 몇 개가 실패했는지
- 어떤 원본 파일을 사용했는지

해결 방향:

`DataSyncRun`이라는 실행 기록을 만든다.

```text
실행 시간
실행 결과
원본 파일명
원본 전체 개수
신규 개수
수정 개수
실패 개수
오류 내용
```

# 6. CI는 왜 필요한가?

## 현재 문제

지금은 `runsv`에 코드를 올리면 Render가 바로 배포할 수 있다.

만약 코드에 오류가 있으면 오류가 있는 코드도 운영 서버에 올라갈 수 있다.

## CI를 추가하면

```text
팀원이 코드 올림
      ↓
GitHub가 자동으로 검사
      ↓
┌ 성공 → 배포 가능
└ 실패 → 배포 중단, 오류 수정
```

## 자동으로 검사할 내용

- Django 설정에 문제가 없는가?
- 모델을 바꾸고 migration 파일을 빼먹지 않았는가?
- 로그인 테스트가 통과하는가?
- 미션과 운동 기록 테스트가 통과하는가?
- 친구와 파티 테스트가 통과하는가?
- CSS와 이미지 파일을 정상적으로 모을 수 있는가?

## 추가할 파일

```text
.github/workflows/ci.yml
```

## 팀에서 결정할 질문

- [ ] 누가 CI 파일을 작성할 것인가?
- [ ] `runsv`에 직접 push하지 못하게 막을 것인가?
- [ ] 한 명 이상의 리뷰가 있어야 병합하게 할 것인가?
- [ ] Selenium 테스트는 나중에 별도로 추가할 것인가?

# 7. CD는 어떻게 구성하는가?

CI가 검사 담당이라면 CD는 배포 담당이다.

권장 흐름:

```text
Pull Request 작성
      ↓
GitHub Actions 검사
      ↓ 성공
runsv에 병합
      ↓
Render가 새 코드 가져오기
      ↓
필요한 패키지 설치
      ↓
DB migration
      ↓
Gunicorn 서버 실행
      ↓
/healthz/ 정상 확인
      ↓
새 버전 공개
```

## Render에서 확인할 내용

```text
Repository: pes9476/netfit
Branch: runsv
Auto-Deploy: After CI Checks Pass
Health Check Path: /healthz/
```

## 실패했을 때 기대하는 동작

| 실패한 부분 | 어떻게 되어야 하는가? |
|---|---|
| 자동 테스트 | 배포 시작 안 함 |
| 패키지 설치 | 새 버전 배포 중단 |
| Migration | 새 서버 시작 안 함 |
| 서버 실행 | 배포 실패 처리 |
| Health Check | 새 버전으로 교체하지 않음 |

# 8. Migration을 어디에서 실행할 것인가?

Migration은 Django 모델 변경을 Supabase DB에 적용하는 작업이다.

예시:

```text
models.py에 period_type 추가
        ↓
migration 파일 생성
        ↓
python manage.py migrate
        ↓
Supabase 테이블에 period_type 컬럼 생성
```

이 작업을 하지 않으면 다음과 같은 오류가 발생할 수 있다.

```text
column fitness_personaldailyquest.period_type does not exist
```

## 유료 Render

Pre-Deploy Command 사용 권장:

```bash
python manage.py migrate --noinput
```

## 무료 Render

Start Command 앞에 연결하는 방법:

```bash
python manage.py migrate --noinput && gunicorn config.wsgi:application --bind 0.0.0.0:$PORT
```

팀에서 결정할 질문:

- [ ] 현재 Render가 무료 플랜인가?
- [ ] Migration을 Build, Pre-Deploy, Start 중 어디에서 실행하고 있는가?
- [ ] Render 배포 로그에서 migration 성공을 확인했는가?

# 9. Cron은 왜 필요한가?

Cron은 정해진 시간에 작업을 자동 실행하는 기능이다.

NETFIT에서는 다음 작업에 사용할 수 있다.

| 작업 | 추천 주기 |
|---|---:|
| 공공체육시설 데이터 갱신 | 주 1회 |
| 시설 운영시간 수집 | 하루 1회 이하 |
| 오래된 초대 정리 | 하루 1회 |
| 고아 이미지 정리 | 주 1회 |

## Cron을 사용하지 않아도 되는 기능

- 날씨: 사용자가 요청할 때 현재 위치로 조회
- 스포츠 뉴스: 요청 시 캐시를 이용해 조회
- 파티 종료 여부: 화면 조회 시 날짜로 바로 계산 가능

## Cron 작업 구조

먼저 Django 명령을 만든다.

```text
fitness/management/commands/sync_facilities.py
```

수동 실행:

```bash
python manage.py sync_facilities
```

수동 실행이 정상인 것을 확인한 뒤 Render Cron 또는 GitHub Actions가 정해진 시간에 이 명령을 실행하게 한다.

## 어떤 방식을 사용할까?

### Render Cron

장점:

- Render에서 한곳에 관리 가능
- 웹 서비스와 비슷한 환경으로 실행

단점:

- 비용이 발생할 수 있음

### GitHub Actions 예약 실행

장점:

- 공모전 단계에서 비교적 간단함
- 실행 결과를 Actions 화면에서 확인 가능

단점:

- GitHub에 운영 DB 접속 정보를 Secret으로 등록해야 함
- 운영 DB 접근 보안을 더 신경 써야 함

# 10. 크롤링은 어떻게 진행할까?

크롤링은 바로 전체 시설에 적용하지 않는다.

## 권장 진행 순서

### 1단계: 필요한 정보 확정

공식 CSV에 없는 정보 중 실제 서비스에 필요한 것을 정한다.

- [ ] 운영시간
- [ ] 휴관일
- [ ] 예약 URL
- [ ] 프로그램 정보

### 2단계: 공식 데이터 확인

같은 정보가 공식 API에 있으면 크롤링하지 않는다.

### 3단계: 소규모 실험

시설 홈페이지 3~5개만 대상으로 정보를 추출한다.

### 4단계: 사이트별 규칙 작성

홈페이지 구조가 다르므로 모든 사이트를 같은 방법으로 처리할 수 있는지 확인한다.

### 5단계: 안전장치 추가

- 요청 간격
- timeout
- 최대 재시도
- 실패 URL 목록
- 수집 시간과 출처 기록
- robots.txt와 이용약관 확인

### 6단계: Cron 연결

수동 실행이 안정적인 것을 확인한 다음 자동 실행한다.

# 14. 이번 주 최소 목표

공모전 일정이 짧다면 모든 항목을 한꺼번에 구현하지 않는다. 다음 네 가지를 최소 목표로 한다.

## 목표 1: CI

```text
코드를 올리면 GitHub가 Django 검사와 테스트를 자동 실행한다.
```

## 목표 2: 안전한 CD

```text
테스트를 통과한 runsv 코드만 Render에 배포한다.
```

## 목표 3: 시설 데이터 정확성

```text
잘못된 지역을 서울로 저장하지 않고 중복 기준을 강화한다.
```

## 목표 4: 수동 동기화 명령

```text
python manage.py sync_facilities
```

이 명령이 안정적으로 동작한 뒤 Cron을 붙인다.

# 16. 발표에서 사용할 쉬운 설명

## 현재 기능

> NETFIT은 KSPO 공공체육시설 CSV를 정리하여 Supabase DB에 저장하고, 사용자의 지역과 위치를 기준으로 주변 체육시설을 추천합니다. 현재 데이터 입력은 CSV 기반 ETL 방식이며, 단순 파일 업로드가 아니라 지역명 정리와 중복 확인 과정을 거칩니다.

## 개선 목표

> 앞으로는 GitHub에서 코드를 자동 검사한 뒤 정상 코드만 Render에 배포하고, 시설 데이터도 정해진 시간에 자동으로 갱신할 예정입니다. 공식 데이터에 없는 운영시간이나 휴관일은 수집 허용 여부를 확인한 뒤 보조적으로 수집할 계획입니다.

## 한 문장 요약

> 코드는 테스트 후 안전하게 배포하고, 시설 데이터는 검증 후 정확하게 저장하며, 필요한 정보만 정해진 시간에 갱신하는 구조를 만드는 것이 목표입니다.
