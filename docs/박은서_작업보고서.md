### 보고서의 근거와 범위

- 이 보고서는 현재 대화에서 확인되는 사용자 요청·오류 화면과 `runsv`의 Git 커밋·검증 문서, AI의 실제 작업 결과 및 Render 배포 확인을 근거로 작성했다. 다른 채팅방이나 팀원의 전체 작업 기록까지 확인한 것은 아니다.
- 작성자의 기여는 문제 발견, 개선 방향 제시, 결과 검수, 재수정·복구 및 배포 요청으로 구분했다. 코드 구현·테스트·Git 작업 중 AI가 수행한 부분은 **AI 도구를 활용한 작업**으로 표시했다. 작성자가 모든 코드를 직접 작성했다고 표현하지 않는다.
- 이전 커밋의 Git 작성자 `netfit`은 개인 실명이나 실제 코드 작성자를 증명하지 않는다. 대화에서 박은서의 요청이 확인되는 작업과 저장소에서만 확인되는 작업을 구분했다. `juntigger` 명의의 후속 커밋은 팀의 변경 사항으로만 설명한다.
- **완료 확인**은 코드나 실행 결과로 확인한 내용, **요청·검토 확인**은 대화에 요구나 논의가 있지만 최종 결과가 확인되지 않은 내용이다.
- 작성 요청서에는 Railway 배포 주소가 있으나, 이번 대화에서 최종 배포를 확인한 서비스는 **Render의 `netfit-production`**이다. 첨부 문서의 완성일·제출 마감·대회 정보는 참고 정보이며, 별도로 검증하지 않았다.

### 2-2. 핏봇 AI 연결 오류 확인과 Gemini 전환 (수정 커밋: 2026-09-23)

#### 기획

- 홈페이지 챗봇이 운동 상담과 안내에 실제로 답변하도록 만들고자 했다.
- 작성자는 무료 Gemini API 키를 발급받아 등록했다고 설명하고, `runsv`의 Fitbot 코드가 Gemini API를 호출하는지 확인·수정하도록 요청했다.
- API는 프로그램끼리 요청과 답변을 주고받는 통로이며, 인증키는 해당 서비스를 사용할 권한을 확인하는 값이다.

#### 작업 → 문제

- 키 등록 후에도 “AI 연결 설정이 필요합니다.”라는 오류가 표시됐다.
- 이후에는 “답변 연결에 실패했어요. 잠시 후 다시 시도해 주세요.”라는 다른 오류가 나타났다.
- 9월 23일 팀의 최초 Fitbot 커밋(`33bc145`)은 Groq LLM과 Supabase 시설 검색을 연결했다. 작성자가 등록한 키는 Gemini용이었으므로 호출 서비스와 키 설정을 확인해야 했다. 다만 이것만이 이후 모든 오류의 원인이라고 단정할 수는 없다.

#### 해결

- 작성자는 오류 화면과 재현 상황을 반복 전달하고, 대상 브랜치가 `testsv`가 아니라 `runsv`임을 명확히 했다.
- AI 도구를 활용한 `2ecf7bd`(후속 반영 `ddf4843`)에서 Fitbot 호출 코드를 Gemini HTTP API로 전환하고 `GEMINI_API_KEY`/`GOOGLE_API_KEY` 설정과 테스트를 수정했다.
- 9월 24일 `juntigger` 명의의 팀 후속 커밋에서는 Groq·Gemini 하이브리드 대체 호출과 환경변수·오류 진단을 추가했다. 현재 코드가 계속 ‘Gemini 전용’이라고 설명하면 정확하지 않다.
- **결과: Gemini 전환 코드는 확인.** 작성자가 반복 제보한 운영 오류의 최종 원인과 실제 챗봇 정상 응답은 [확인 필요]. 코드 수정과 운영 정상화를 구분한다.

#### [시각화] 이 작업을 그림으로 그린다면

- 추천 그림 종류: 시퀀스(순서도).
- 요소: 사용자 질문 → 챗봇 위젯 → 서버의 AI 연결 설정 확인 → 외부 AI 호출 → 답변 또는 오류 표시.
- 주의: Gemini 호출 성공은 확인되지 않았으므로, 그림에서 ‘점검 대상 흐름’으로 표시한다.

### 2-3. 캐릭터 이름과 챗봇 표시 이름 통일 (수정 커밋: 2026-09-23)

#### 해결

- Gemini 전환과 같은 `2ecf7bd` 커밋에서 챗봇 위젯·폼·모델·여러 화면의 이름과 관련 테스트를 함께 고쳤다.
- 이후 제공된 챗봇 화면에서 백호·포동·토리·아콩의 표시를 확인했다.

- **결과: 9월 23일 코드 변경과 확인한 화면의 이름 통일은 확인.** 프로젝트 전체 문자열의 전수검사 여부는 [확인 필요].

### 2-4. 종료된 내기 파티의 그룹원 목록 표시 개선 (수정 커밋: 2026-09-23)

#### 기획

- 이미 내기가 끝난 파티가 그룹원 목록에 계속 남아 있는 문제를 줄이고자 했다.
- 작성자는 `runsv` 수정, 커밋·푸시, Render 재배포까지 요청했다.

#### 작업 → 문제

- 작성자가 새로고침한 뒤에도 종료된 파티로 보이는 목록이 남아 있는 화면을 전달했다.
- “수정이 안 된 것 같은데 오류인지, 기다리면 바뀌는지”를 물으며 반영 상태를 확인했다.

- `ca2ac6e`에서 종료 시각을 기준으로 상단 그룹원 목록을 필터링하고 관련 테스트를 추가했다. `42dfa45`에서 필터 결과가 빈 목록일 때 전체 파티로 되돌아가는 템플릿의 대체 경로를 제거했다.
- **결과: 코드 수정과 회귀 테스트 추가 확인.** 당시 Render 반영 및 운영 계정 화면에서 최종적으로 숨겨졌는지는 [확인 필요].
- 여기서 ‘없어지게’라는 요청은 화면 목록에서 제외하는 요구로 정리하며, 파티·회원 데이터를 실제 삭제했다고 주장하지 않는다.

- 주의: 코드의 필터·빈 목록 처리 완료와 운영 화면 검증 여부를 따로 표시한다.

### 2-5. 공공 체육시설 CSV 동기화와 자동화 범위 구분 (구현 기록: 2026-09-22~23)

#### 기획

- 주변 시설 안내에 쓰는 공공데이터를 검증하고 반복 반영할 수 있도록 만들고자 했다.
- 작성자는 API 인증키를 발급받기 어려운 상황을 설명하고, 문화 빅데이터 플랫폼의 ‘전국공공체육시설 데이터’ 화면을 제시했다.

#### 작업 → 문제

- 제시된 화면에는 CSV 형식, 무료 제공, 연 단위 갱신 정보가 표시돼 있었다. 이는 당시 화면에 표시된 정보이며 현재 제공 조건을 별도 검증한 것은 아니다.
- 작성자는 다운로드하려면 로그인이 필요하다고 설명했다.
- 사람이 로그인해 매번 파일을 내려받아야 한다면, 데이터 수집부터 서비스 반영까지 전 과정이 자동이라고 말하기 어렵다는 문제를 제기했다.
- 앞선 9월 22일 `711a2ff` 커밋에는 CSV를 확보한 뒤 검증·동기화하는 명령, 원본 ID·중복 관리, 실행 결과 기록(`DataSyncRun`)과 테스트가 추가돼 있다. `288e98d`에는 수동 실행용 GitHub Actions 워크플로가 있다. 이 커밋의 `netfit` 작성자명만으로 박은서의 직접 코드 작성 여부를 확정할 수는 없다.

#### 해결

- 원본 파일 확보와 확보된 CSV의 검증·DB 반영을 분리했다. 9월 22일 검증 문서에는 로컬 SQLite에서 CSV 44,612행을 처리하고 실패 0건으로 재실행 중복 방지를 확인한 기록이 있다. 이것은 운영 DB 반영 성공 증거가 아니다.

### 2-8. 캐릭터별 아이템 착용 방식 개선 및 반복 검수 (날짜: 2026-09-28, 최초 요청일 미상)

#### 기획

- 모자처럼 다른 아이템도 캐릭터에 자연스럽게 붙어 보이게 만드는 것이 목표였다.
- 작성자는 사진에 있는 아이템뿐 아니라 전체 아이템을 대상으로 요청했고, 작업 중 착용 예시를 보여 달라고 했다.
- 특히 밴드는 이마, 선글라스는 눈, 헤드셋은 귀에 각각 위치하면서 동시에 착용할 수 있어야 했다.

#### 작업 → 문제

- 처음 결과는 캐릭터마다 장비가 떠 보이거나, 밴드·마스크·목걸이가 얼굴 위에 겹쳐 보였다.
- 작성자는 “하나도 안 맞는다”, “각각 자연스럽게 착용하게 나와야 한다”며 결과를 반려했다.
- AI가 확인한 문제는 캐릭터와 장비의 크기·위치 기준이 서로 다르고, 움직임도 분리돼 있다는 점이었다.
- 장비만 따로 분리한 이미지에서도 원래 착용 위치가 달라져, 임의의 이동·축소 보정값을 계속 추가하는 방식으로는 일관된 결과를 얻기 어려웠다.
- 중간에 이전 코드로 복구했으나, 마지막 커밋 자체에 이미 수정 코드가 포함돼 있었다. 그 이전 커밋으로 다시 되돌린 뒤에도 사용자가 기대한 자연스러운 착용 상태는 아니었다.

#### 해결

- 작성자가 다시 자연스러운 착용 수정을 요청한 뒤, AI 도구를 활용해 표시 구조를 변경했다.
- 이미 캐릭터에 맞춰진 착용 원본 이미지를 활용하고, 필요한 부위만 화면에 표시하도록 했다. 캐릭터와 장비를 따로 재배치하지 않고 같은 좌표 기준에서 겹쳐 보여주는 방식이다.
- SVG는 그림의 위치와 표시 영역을 코드로 지정하는 형식이다. 이번에는 기존 이미지를 SVG 안에 배치하고, 밴드·안경·헤드셋 등 필요한 영역만 보이게 했다. 실제 3D 모델에 장비를 입히는 시스템을 만든 것은 아니다.
- 네 캐릭터별 표시 영역과 앞뒤 순서를 정하고, 하나의 움직임을 적용해 캐릭터와 장비가 함께 움직이도록 했다.
- 임의의 위치 보정값을 누적하는 방식 대신, 참고 이미지에 있던 원래 착용 관계를 유지하는 방식을 선택했다.
- 검수 중 운동복·벨트 조합에서 벨트 이미지가 주변 옷까지 덮는 문제가 발견돼, 벨트 외곽에 맞게 표시 경계를 좁혔다.
- 별도 미리보기와 실제 피팅룸이 같은 표시 코드를 사용하도록 연결했다.
- **결과: 완료 확인.** 네 캐릭터의 밴드·선글라스·헤드셋 단독 및 동시 착용, 밴드·마스크·목걸이, 운동복·벨트·글러브, 날개·망토·검, 모자·왕관 등의 대표 화면을 확인했다. 실제 콩아 계정의 로컬 피팅룸에서도 토리의 얼굴 장비 3종을 확인했다.

## 3. 전체 흐름 시각화 재료 (한 번만 작성)

### (A) 전체 서비스 아키텍처 (기술 구조도용)

- 프론트엔드: Django 템플릿 기반 HTML, CSS, JavaScript. 꾸미기에는 SVG 표시 영역과 캐릭터·장비 PNG 이미지 사용.
- 백엔드: Python·Django. 꾸미기 화면에서 장착 목록을 전달하고, 장착·해제 요청에 응답하는 구조를 확인했다.
- 데이터: 사용자 프로필의 착용 목록과 아이템 구매 정보, 시설 데이터와 동기화 실행 기록. Fitbot의 시설 검색에 Supabase가 사용된 팀 커밋은 있으나 운영 DB 연결 구조 전체와 작성자별 기여는 [확인 필요].
- 형상 관리: Git·GitHub, 테스트용 `testsv`와 운영 대상 `runsv`를 구분.
- 배포: Render `netfit-production`. 배포 로그에서 정적 파일 수집과 Gunicorn을 통한 Django 실행을 확인했다.

## 4. "별거 아닌 기술을 기발하게 썼다" 어필 포인트

### 사례 1. 새 3D 시스템 대신 기존 착용 이미지와 표시 영역 활용

- 상황: 동물마다 얼굴·귀·몸 위치가 달라 같은 장비 이미지를 같은 좌표에 붙이면 자연스럽지 않았다.
- 아이디어: 이미 잘 맞춰진 착용 원본에서 필요한 부위만 보여주고, 캐릭터와 장비의 좌표·움직임을 하나로 묶었다.
- 결과: 별도의 실시간 3D 장착 엔진 없이 밴드·안경·헤드셋의 단독·동시 착용을 네 캐릭터에서 확인했다. 개발 시간이나 비용 절감량을 수치로 측정한 기록은 없다.

### 사례 2. 같은 코드를 쓰는 ‘구매 없는 미리보기’

- 상황: 실제 계정만으로는 보유 아이템과 포인트 때문에 다양한 조합을 확인하기 불편했다.
- 아이디어: 실제 피팅룸의 표시 코드를 로컬 미리보기에서도 그대로 사용했다.
- 결과: 포인트 지급이나 구매 없이 네 캐릭터의 착용을 비교할 수 있었다. 모양만 비슷한 별도 시안과 실제 화면 사이의 차이를 줄이는 검수 기반을 마련했다.

### 사례 3. 사용자의 캡처를 구체적인 합격 기준으로 바꾸기

- 상황: “자연스럽게”라는 표현만으로는 구현 결과의 적절성을 판단하기 어려웠다.
- 아이디어: 작성자가 캡처와 반복 피드백으로 “밴드는 이마, 안경은 눈, 헤드셋은 귀”라는 확인 가능한 기준을 제시했다.
- 결과: 단순히 착용 개수가 표시되는 것과 실제 착용 위치가 맞는 것을 구분해 검수했다. 이는 작성자의 문제 정의와 품질 확인 기여다.

### 사례 4. 로그인 제약을 인정하고 CSV 확보와 반영을 분리

- 상황: 인증키가 없고 제시된 자료 사이트는 다운로드에 로그인이 필요했다.
- 아이디어: 원본 확보가 수동일 수 있음을 숨기지 않고, 확보한 CSV의 검증·중복 처리·동기화·실행 기록을 별도 단계로 구성했다.
- 결과: 9월 22일 코드와 로컬 검증 기록을 확인했다. 제공 사이트의 무인 다운로드나 운영 DB 자동 갱신까지 박은서의 성과로 단정하지 않는다.
