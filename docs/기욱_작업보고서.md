## 2. 작업별 상세 (기획 → 작업 → 문제 → 해결)

### Supabase 환경 구축과 Django DB 연결 (날짜: 2026-09-15 설정 구현, 9월 18일 연결 확인 기록, 9월 21일 배포 연결 검증)

#### 기획
- 서비스 계정과 운동·미션 데이터를 함께 저장하고 배포 환경에서도 사용할 DB 기반이 필요했다.
- 작성자는 Supabase 환경 구축과 DB 연결을 수행하고, 로컬 개발·테스트와 실제 서비스 DB의 역할을 구분해 점검했다.

#### 작업 → 문제
- 초기 SQLite 전용 설정에서 PostgreSQL도 사용할 수 있도록 전환해야 했다.
- 같은 코드를 가져와도 연결 DB가 다르면 회원 계정과 운동 기록이 다르게 보이는 혼동이 있었다.
- DB 접속 정보는 코드와 분리해야 했으며, 소스코드 동기화만으로 실제 DB 구조와 데이터까지 최신화되지는 않았다.

#### 해결
- 9월 15일 `99f204c`에서 `.env` 읽기, PostgreSQL 연결 변수, SQLite 대체 경로 및 관련 패키지를 반영했다.
- 9월 18일 체크리스트에 Supabase PostgreSQL 연결과 운영 DB 마이그레이션 적용을 기록했다.
- 9월 21일 `a0fd691`에서 `DATABASE_URL` 연결 문자열 처리와 SSL 설정을 추가했다. 당시 회고에는 배포 웹에서 새 계정 생성 후 Supabase 테이블에 계정·연결 데이터가 생성되는 것을 확인했다고 기록되어 있다.
- “코드는 Git, 실행은 배포 서버, 데이터는 Supabase”로 구분해 연결 문제를 점검했다. Supabase 프로젝트 최초 생성일은 Git으로 확인되지 않는다.
- 근거: `99f204c`, `a0fd691`, `docs/BACKEND_IMPLEMENTATION_CHECKLIST.md`, `docs/NETFIT_PROJECT_RETROSPECTIVE.md`의 9월 21일 기록.

#### [시각화] 이 작업을 그림으로 그린다면
- 추천 그림 종류: 아키텍처 다이어그램.
- 요소: `사용자 → Django 서버 → 환경변수의 DB 연결 정보 → Supabase PostgreSQL`. 별도로 `테스트 → 격리 SQLite`를 표시한다.

### 서비스 기능을 저장하는 DB 모델과 관계 구성 (날짜: 2026-09-15)

#### 기획
- 화면에서 선택한 운동 모드와 미션·파티·배틀 참여 상태를 지속적으로 저장할 구조가 필요했다.

#### 작업 → 문제
- 기존 프로필·파티 구조에 온보딩 상태, 참여자, 인증 제출 등을 표현할 항목과 관계를 추가해야 했다.
- 같은 사용자가 같은 미션이나 배틀에 중복 등록되지 않도록 저장 단계의 제한이 필요했다.

#### 해결
- `99f204c`에서 프로필의 온보딩·활동 모드·접근성 관련 필드와 파티 소유자·정원·생성 시각을 추가했다.
- `Mission`, `MissionParticipant`, `BattleRoom`, `BattleParticipant`, `ProofSubmission` 모델과 마이그레이션을 추가했다.
- 미션·사용자 및 배틀·사용자 조합에 중복 방지 제약을 두었다.
- 이는 DB 구조 구현 성과다. 해당 모델을 이용한 모든 화면·업무 흐름이 당시 완성됐다는 뜻은 아니며, 이후 기능 구현 점검을 별도로 수행했다.

#### [시각화] 이 작업을 그림으로 그린다면

### 관리자 계정 생성과 관리 콘솔 확인 (날짜: 정확한 실행일 확인 필요)

#### 기획
- 일반 사용자 화면뿐 아니라 관리자 관점에서 계정과 서비스 데이터를 확인할 수 있는 점검 환경을 마련하려 했다.

#### 작업 → 문제
- 코드가 실행되는 것만으로 실제 DB 연결·저장 성공을 확인할 수 없어 관리자 화면과 DB 콘솔 확인이 필요했다.
- 계정 생성과 콘솔 조작은 DB·외부 서비스의 상태 변경이라 Git 커밋에 실행 시각이 남지 않는다.

#### 해결
- 작성자 설명에 따라 관리자 계정 생성과 관리 콘솔 확인을 수행 사실로 기록한다.
- 저장소에는 Django `/admin/` 경로와 프로필·캐릭터·운동 기록·배지·시설·파티 등 모델의 관리자 등록이 확인된다. 이는 관리자 기능의 코드 근거이며, 계정 생성일을 증명하는 기록은 아니다.
- Supabase 연결 확인은 당시 문서의 계정 생성·DB 저장 검증 기록으로 보완한다.
- 관리자 계정의 정확한 생성일, Django 관리자와 Supabase 콘솔 각각의 점검일, 개별 화면의 캡처는 [확인 필요]. 계정명·비밀번호·접속 비밀정보는 보고서에 싣지 않는다.

#### [시각화] 이 작업을 그림으로 그린다면
- 추천 그림 종류: 플로우차트.
- 요소: `관리자 계정 준비 → 관리 화면 접속 → 서비스 데이터 확인 → DB 저장 상태와 대조 → 오류 발견 시 개선 요청`.

### 백엔드 기능 점검·테스트·개선 지시의 반복 (날짜: 2026-09-18 점검 기록, 이후 지속 수행)

#### 기획
- 화면이 있다는 이유만으로 기능을 완료로 보지 않고, 인증·권한·DB 저장·중복 방지·테스트 결과를 함께 확인하려 했다.
- 작성자는 서비스 사용과 관리 콘솔 확인을 통해 불안정하거나 빠진 부분을 찾아 수정·업데이트를 요청하고, 반영 결과를 반복 확인하는 역할을 수행했다.

#### 작업 → 문제
- 계정·온보딩·운동 기록·미션·친구·파티·랭킹·시설 검색·외부 API의 구현 수준이 달랐다.
- 서버 기준 타이머, 사진 저장·접근 권한, XP 지급 연결, 데모 랭킹 구분 등 당시 미완료 또는 추가 확인 대상이 발견됐다.
- Selenium 브라우저 테스트는 ChromeDriver 다운로드 환경 문제로 실행되지 않았고, 서버 테스트와 구분할 필요가 있었다.

#### 해결
- 9월 18일 발표 점검 기록과 구현 체크리스트에 완료·부분 구현·후속 개선을 구분해 정리했다. 체크리스트 커밋은 9월 21일 `bad1895`이며 문서의 점검 기준일은 9월 18일이다.
- 당시 문서에는 백엔드 테스트 39개 통과와 Django 검사 통과가 기록되어 있다. 테스트는 격리 SQLite에서 수행했으며 Supabase 운영 DB 전체 테스트 통과를 뜻하지 않는다.
- 점검 문서의 일부 본문에는 이전 31개 실행 출력과 개선 전 설명도 남아 있다. 39개는 상단 수정 요약·체크리스트 기준의 기록으로 제시하며, 서로 다른 단계의 수치를 합산하지 않는다.
- 미션·초대·사진 검증 등은 실제 수정으로 연결했고, 타이머·Storage·백업 등은 후속 과제로 구분했다. 당시 미완료 항목이 현재도 미완료인지는 별도 확인이 필요하다.
- 결과적으로 작성자의 역할은 단순 코드 병합뿐 아니라 “기능 확인 → 문제 제기 → 개선 요청 → 수정 반영 → 재점검”의 지속적인 백엔드 품질 점검이었다.

### 미션·친구·파티·인증사진의 안정성 보강 (날짜: 2026-09-18)

#### 기획
- 미션 완료나 초대 수락을 여러 번 요청해도 데이터가 중복되거나 상태가 어긋나지 않도록 개선하려 했다.

#### 작업 → 문제
- 미션 완료, 배지 지급, 운동 기록이 일부만 저장되면 데이터가 불일치할 수 있었다.
- 잘못된 미션 종류·명령, 미완료 미션의 사진 삭제 처리, 중복 친구 요청·파티 초대, 동시 초대 수락을 점검할 필요가 있었다.
- 업로드 파일을 사진으로 믿고 받아들이지 않도록 검증이 필요했다.

#### 해결
- `53f85c8`에서 미션 완료·배지·운동 기록을 트랜잭션으로 묶었다. 트랜잭션은 관련 저장 작업을 한 묶음으로 성공시키거나 취소하는 방식이다.
- 잘못된 요청 경로를 차단하고, 친구 요청·파티 초대에 응답 시각 및 대기 중복 방지 DB 제약을 추가했다. 자기 자신에 대한 친구 요청도 DB에서 막았다.
- 파티 수락 시 종료 여부·정원을 재검사하고 행 잠금으로 동시 처리 충돌을 줄였다.
- 인증사진에 실제 이미지 여부, JPEG·PNG·WebP 형식, 최대 5MB 제한을 적용하고 관련 테스트를 추가했다.
- 당시 점검 기록에는 Supabase에 `0015` 적용, 후속 체크리스트에는 `0016`까지 적용했다고 기록되어 있다.

- Supabase에 계정이 있다는 설명만으로는 실제 로그인에 사용되는 계정 저장 위치를 알 수 없었다.
- 로그인 뷰, 가입 폼, 카카오 가입 코드와 인증 테스트를 읽었다.

#### 해결
- 현재 일반 로그인은 Django `AuthenticationForm`과 `auth_user`를 사용한다는 점을 확인했다.
- Supabase Auth 계정과 Django 계정의 혼동, 비밀번호를 DB에 일반 문자열로 직접 입력한 경우, 카카오 가입으로 일반 비밀번호가 없는 경우를 후보로 설명했다.
- 비밀번호 해시는 원문 비밀번호 대신 검증용으로 저장하는 값이며, DB 칸에 평문 비밀번호를 넣는 방식으로는 정상 인증되지 않는다.
- 사용자가 확인한 화면이 Authentication인지 `auth_user` 표인지 질문했다. 후속 답변과 실제 계정 점검은 없어 원인 확정·비밀번호 변경·로그인 복구는 미완료다.

#### [시각화] 이 작업을 그림으로 그린다면
- 추천 그림 종류: 플로우차트.
- 요소: `일반 로그인 입력 → Django 인증 → auth_user 검증 → 로그인 성공 또는 실패`. 옆에 `Supabase Auth와 별개`, `카카오 가입 계정은 일반 비밀번호 유무 확인` 표시.
