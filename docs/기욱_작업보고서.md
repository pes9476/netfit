### 공통 브랜치 변경 반영과 로컬 작업 보존 (날짜: 2026-09-23)

#### 기획

#### 작업 → 문제
- `git pull --no-rebase origin runsv`를 실행했다.
- Git 기록 폴더 쓰기 권한이 없어 처음에는 `cannot open '.git/FETCH_HEAD': Permission denied`가 발생했다.
- 권한 승인 후에는 로컬의 `NETFIT_TESTSV_PIPELINE_EXECUTION_SCRIPT.md`가 원격 파일과 이름이 같아 덮어쓰기 방지로 중단됐다.
- 문서를 백업한 뒤 `.env.example`, `config/settings.py`, `import_facilities.py`에서 충돌이 발생했다.

#### 해결
- 필요한 Git 쓰기 권한을 승인받아 실행했다.
- 로컬 문서를 날짜·시간이 들어간 별도 백업 파일로 이동해 내용을 보존했다.
- 충돌 구간을 확인하고 `runsv`의 최신 배포 판별 및 시설 가져오기 처리에 맞춰 정리했다.
- 백업 파일은 커밋·push에서 제외했다. 원본과 백업을 모두 보존했으며, 문서 내용의 통합은 하지 않았다.
- 마이그레이션 문제까지 정리한 후 병합 커밋 `1dd8dbb`를 생성하고 원격에 반영했다.

### 서로 갈라진 DB 변경 이력 연결 (날짜: 2026-09-23)

#### 기획
- 병합한 코드가 함께 동작하는지 배포 설정과 시설 동기화 테스트로 확인하려 했다.
- 마이그레이션은 DB 표와 항목을 어떤 순서로 바꾸는지 기록한 파일이다.

#### 작업 → 문제
- 테스트 실행 전 `multiple leaf nodes in the migration graph` 오류가 발생했다.
- 기존 `0020_merge_20260922_1100`과 가져온 `0023_align_facility_source_ids`가 각각 마지막 변경 이력으로 남아 있었다.

#### 해결
- 양쪽 변경 내용을 확인한 뒤 `makemigrations fitness --merge --noinput --skip-checks`로 두 이력을 연결했다.

- `--skip-checks`는 생성 명령의 사이트 검사를 건너뛴 것이며, 누락 패키지를 해결하거나 테스트 통과를 보장한 것은 아니다.
- 9월 23일 테스트는 완료하지 못했다. 운영 DB에 이 파일을 적용했는지는 [확인 필요].

### ‘짱구’ 계정 로그인 실패 원인 점검 (날짜: 추정 2026-09-23)

#### 기획
- 이름은 맞는데 비밀번호로 로그인되지 않는다는 문제를 제기하고 원인을 확인하려 했다.

#### 작업 → 문제
- Supabase에 계정이 있다는 설명만으로는 실제 로그인에 사용되는 계정 저장 위치를 알 수 없었다.
- 로그인 뷰, 가입 폼, 카카오 가입 코드와 인증 테스트를 읽었다.

#### 해결
- 현재 일반 로그인은 Django `AuthenticationForm`과 `auth_user`를 사용한다는 점을 확인했다.
- Supabase Auth 계정과 Django 계정의 혼동, 비밀번호를 DB에 일반 문자열로 직접 입력한 경우, 카카오 가입으로 일반 비밀번호가 없는 경우를 후보로 설명했다.
- 비밀번호 해시는 원문 비밀번호 대신 검증용으로 저장하는 값이며, DB 칸에 평문 비밀번호를 넣는 방식으로는 정상 인증되지 않는다.
- 사용자가 확인한 화면이 Authentication인지 `auth_user` 표인지 질문했다. 후속 답변과 실제 계정 점검은 없어 원인 확정·비밀번호 변경·로그인 복구는 미완료다.

#### [시각화] 이 작업을 그림으로 그린다면
- 추천 그림 종류: 플로우차트.
- 요소: `일반 로그인 입력 → Django 인증 → auth_user 검증 → 로그인 성공 또는 실패`. 옆에 `Supabase Auth와 별개`, `카카오 가입 계정은 일반 비밀번호 유무 확인` 표시.

## 3. 전체 흐름 시각화 재료 (한 번만 작성)

### (A) 전체 서비스 아키텍처 (기술 구조도용)
- 화면: Django HTML 템플릿과 CSS. 대시보드·로그인·시설·랭킹 등 템플릿이 저장소에 있다.

- DB: 프로젝트 문서는 Supabase PostgreSQL 연결 구조를 설명한다. 이번 테스트는 `USE_SQLITE=True`로 별도 테스트 DB를 사용했다. 현재 운영 연결 상태는 [확인 필요].
- 배포: 확인한 프로젝트 문서·설정은 Render 중심이다. 요청서 참고 자료에는 Railway 주소가 있어 최종 발표용 운영 주소는 [확인 필요].

- 협업: Git/GitHub, `runsv`와 개인 작업 브랜치 `netfit_giuk`.
- 연결: `사용자 → Django 화면·서버 → PostgreSQL(Supabase)` / `시설 CSV → Django 관리 명령 → 시설 DB` / `GitHub → 배포 환경(Render, 실제 배포 확인 필요)`.
- 발표 시 “기존 프로젝트 구조”로 표시한다. 전체 구조를 작성자가 직접 구축했다고 표현하지 않는다.

## 4. "별거 아닌 기술을 기발하게 썼다" 어필 포인트

### 사례 1. 파일 이름을 바꿔 로컬 작업 보존 — 실제 수행
- 상황: 팀 파일과 로컬 문서의 이름이 같아 병합이 중단됐다.
- 아이디어: 로컬 파일에 날짜·시간을 붙여 백업하고 원격 파일을 정상적으로 가져왔다.
- 결과: 로컬 문서를 잃지 않고 병합을 계속했다. 복잡한 복구 도구 없이 파일 이동으로 덮어쓰기 위험을 피했다.

### 사례 2. 자동화의 범위를 바꾸기 — 검토 단계
- 상황: API 키 발급과 로그인 때문에 시설 데이터 수집 자동화가 어려웠다.
- 아이디어: 파일 확보와 이후 처리를 분리하고, 기존 CSV 처리 코드를 이용해 검사·비교·DB 반영을 자동화하는 방향을 검토했다.
- 결과: 외부 수집이 막혀도 자동화할 수 있는 작업 범위를 정리했다. 아직 구현·시간 절약 효과는 확인하지 않았다.

### 사례 3. 간단한 문서를 팀 공유 자료로 활용 — 반영 확인
- 상황: 파이프라인과 팀 작업 안내 문서가 로컬 파일로 남아 있었다.
- 아이디어: Markdown·HTML 문서 4개를 코드와 같은 Git 저장소에서 관리했다.
- 결과: 개인 브랜치에 문서 버전을 남기고 원격 공유가 가능한 상태로 만들었다. 팀원의 실제 활용 여부는 [확인 필요].

- 유료 서비스를 무료 방식으로 교체해 운영한 사례: 해당 없음 — 대체 데이터 검토만 확인된다.
- 포기하려던 기능을 다른 방식으로 구현 완료한 사례: 해당 없음 — 이번 기록에서는 확인되지 않는다.
