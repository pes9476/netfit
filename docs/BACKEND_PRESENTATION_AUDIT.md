## 3. 계정과 사용자 데이터

### 처리 절차

1. 일반 회원가입은 `register_view`가 `RegisterForm.save()`를 호출한다.
2. 카카오 로그인은 OAuth callback에서 카카오 사용자 ID를 검증한다.
3. 신규 카카오 사용자는 Django 기본 User를 만든 뒤 `KakaoAccount`와 연결한다.
4. User 생성 signal이 `Profile`과 `CharacterCard`를 자동 생성한다.
5. 로그인 후 온보딩 완료 여부에 따라 대시보드 또는 온보딩으로 이동한다.

### 주요 DB 테이블

| 테이블 | 역할 |
|---|---|
| `auth_user` | 계정, 비밀번호 해시, 활성 상태, 가입일 |
| `fitness_kakaoaccount` | Django 사용자와 카카오 ID 연결 |
| `fitness_profile` | 지역, 신체 정보, 운동 모드, 온보딩 상태 |
| `fitness_charactercard` | 레벨, 경험치, 카드 상태 |

### 발표 시 확인 화면

- 회원가입 전후 `auth_user` 행 수
- 같은 사용자 ID의 `Profile`, `CharacterCard` 생성 여부
- 카카오 계정의 비밀번호 미사용 상태와 `KakaoAccount.user_id` 연결
- 로그아웃 후 세션 접근 차단

## 4. 솔로 모드

### 처리 절차

1. 사용자가 솔로 모드를 선택한다.
2. 시설 찾기, AI 추천, 직접 입력 중 하나를 선택한다.
3. AI 추천은 연령 조건으로 산책 20분 또는 러닝 30분을 생성한다.
4. 직접 입력은 제목, 운동 종류, 5~300분 범위를 검증한다.
5. `PersonalDailyQuest`를 저장하고 온보딩을 완료한다.

### 확인 포인트

- 현재 AI 추천은 외부 AI API가 아니라 조건문 기반 추천이다.
- 개인 미션 완료 시 `BadgeAward.get_or_create()`로 중복 보상을 막는다.
- 솔로 모드 자동 테스트는 통과했다.

## 5. 파티 모드와 그룹 미션

### 처리 절차

1. 친구 목록에서 초대 대상을 선택한다.
2. 파티 이름, 시작일, 종료일, 내기 보상을 입력한다.
3. 날짜와 초대 대상이 유효한지 검증한다.
4. transaction 안에서 `Party`와 멤버 관계를 저장한다.
5. 파티 소유자가 그룹 일일 미션을 생성한다.
6. 파티 멤버만 그룹 미션을 완료하고 배지를 받을 수 있다.

### 수동 점검 시나리오

- 사용자 A와 B를 만든다.
- A가 B를 친구로 추가한다.
- A가 B를 초대해 파티를 만든다.
- 종료일이 시작일보다 빠른 입력이 거절되는지 확인한다.
- A가 그룹 미션을 생성한다.
- B가 미션을 완료하고 배지를 받는지 확인한다.
- B가 같은 미션을 다시 완료해도 배지가 추가되지 않는지 확인한다.
- 초대되지 않은 C가 파티 미션에 접근할 수 없는지 확인한다.

### 현재 부족한 부분

- 파티 생성·초대·권한에 대한 전용 자동 테스트가 없다.
- 초대 수락 단계 없이 파티 생성자가 친구를 즉시 멤버로 추가한다.
- 파티 최대 인원 필드가 있지만 생성 과정에서 인원 제한 검증을 별도로 확인해야 한다.

## 6. 친구 추가

### 현재 동작

- 닉네임을 대소문자 구분 없이 검색한다.
- 존재하지 않는 사용자, 자기 자신, 이미 등록된 친구를 거절한다.
- 성공 시 A→B와 B→A 두 개의 `FriendLink`를 생성해 양방향 관계로 표현한다.
- DB unique constraint가 동일 방향의 중복 링크를 막는다.

### 추가해야 할 자동 테스트

- 정상 양방향 친구 추가
- 자기 자신 추가 거절
- 존재하지 않는 닉네임 거절
- 중복 추가 시 행 수 불변
- 로그인하지 않은 사용자 접근 차단
- 동시에 같은 친구를 추가할 때 중복·오류 처리

## 7. 랭킹

### 실제 계산 방식

- 지역 랭킹: 현재 사용자와 같은 `Profile.area`
- 파티 랭킹: 현재 사용자와 같은 파티에 속한 사용자
- 친구 랭킹: `FriendLink`로 연결된 사용자와 본인
- 점수: 사용자가 받은 모든 `BadgeAward.points` 합계
- `rank_participation=True` 사용자만 대상

### 발표 시 반드시 밝힐 사항

- 현재 별도의 `nation` scope는 없다.
- 지역 랭킹에는 실제 사용자와 `DEMO_RANKINGS` 데이터가 함께 들어갈 수 있다.
- 친구 랭킹에도 데모 상위 3명이 추가된다.
- 따라서 현재 화면을 순수 운영 DB 기반 “전국 실시간 랭킹”이라고 설명하면 정확하지 않다.
- 실시간 push가 아니라 페이지를 요청할 때 DB를 다시 집계하는 방식이다.

### 개선 점검 항목

- 데모 데이터와 실제 데이터를 화면에서 명확히 구분하거나 운영 모드에서 제외
- 전국 scope 추가 여부 결정
- 사용자 수 증가 시 N+1 집계 개선
- 동점 순위 정책 정의
- 랭킹 집계 캐시와 갱신 주기 정의
- 지역·파티·친구 scope 전용 테스트 추가

## 8. 내기·배틀 시뮬레이션

### 현재 구현

- 사용자 운동 기록으로 속도, 체력, 동기 수치를 계산한다.
- 전투력은 `속도 40% + 체력 35% + 동기 25% + 레벨 보정`이다.
- 일반 배틀 생성 시 상대 전투력과 레벨에 난수를 더한다.
- 생성 즉시 `is_finished=True`로 저장한다.
- 데모 배틀은 미리 정의한 상대와 보상을 사용한다.

### 발표 표현

현재 코드는 “운동 기록 기반 카드 전투력과 상대 데이터를 생성·기록하는 시뮬레이션”이다. 승자 판정, 보상 정산, 동의, 결과 확정 절차까지 구현한 실제 내기 엔진은 아니다.

### 추가해야 할 자동 테스트

- 전투력 공식의 경계값과 재현성
- 지역 배틀 레벨 5 제한
- 다른 사용자의 배틀 결과 접근 차단
- 커스텀 보상과 기본 보상 저장
- 승패 판정이 필요하다면 명시적 결과 필드와 결정 규칙
- 금전성 보상 제한과 서비스 정책 검토

## 9. API와 외부 데이터

| API | 내부 경로 | 외부 서비스 | 인증 | 캐시·갱신 | 현재 테스트 |
|---|---|---|---|---|---|
| 카카오 로그인 | `/login/kakao/`, callback | Kakao OAuth | state, 세션, callback | 요청 시 | O, mock 사용 |
| 날씨 | `/api/weather/` | Open-Meteo | 현재 로그인 필수 아님 | 요청 시 | 없음 |
| 역지오코딩 | 날씨 서비스 내부 | Nominatim, BigDataCloud | User-Agent 사용 | 요청 시 | 없음 |
| 스포츠 뉴스 | `/api/news/` | Google News RSS | 로그인 필요 | 메모리 10분, 강제 갱신 최소 45초 | 없음 |

### API 공통 점검표

- 정상 응답의 status code, Content-Type, JSON schema
- 필수·선택 query parameter 검증
- timeout과 외부 서비스 장애 시 fallback
- 외부 응답 값의 타입과 범위 검증
- 인증·권한·CSRF 정책
- rate limit과 과도한 호출 방지
- 로그에 token, secret, 개인정보가 남지 않는지 확인
- 운영 환경의 API 키와 redirect URI 분리
- 응답 시간과 캐시 적중 여부 기록

### 발견된 주의점

- 날씨 API는 좌표 변환 실패나 Open-Meteo 장애 시 기본값 형태로 응답할 수 있어 실패 여부가 사용자에게 명확하지 않다.
- 스포츠 뉴스 캐시는 서버 프로세스 메모리에만 있다. 서버 재시작 시 사라지고, 여러 프로세스에서는 캐시가 서로 다를 수 있다.
- 외부 API 전용 자동 테스트와 응답 schema 테스트가 없다.

## 10. 데이터 갱신과 “실시간” 범위

| 데이터 | 갱신 시점 | 방식 | 실시간 수준 |
|---|---|---|---|
| 계정·친구·파티·운동·배지 | 사용자 요청 처리 직후 | DB write | 다음 요청부터 반영 |
| 랭킹 | 랭킹 페이지 요청 시 | DB 재집계 | 새로고침 기반 |
| 날씨 | 브라우저 위치 획득 후 API 요청 | HTTP fetch | 요청 시 최신 조회 |
| 스포츠 뉴스 | 화면 요청·새로고침 | HTTP fetch + 10분 메모리 캐시 | 준실시간 |
| 대시보드 뉴스 표시 | 브라우저 timer | `setInterval`로 화면 롤링 | 표시만 주기 변경 |

현재 WebSocket, Server-Sent Events, Django Channels, background worker는 없다. 따라서 발표에서는 “실시간 스트리밍”보다 “요청 시 최신 데이터 조회” 또는 “주기적 화면 갱신”이라고 표현한다.

## 11. 발표 전 백엔드 점검 순서

1. `git status`와 배포 대상 commit을 기록한다.
2. 환경변수에서 DEBUG, DB, Kakao redirect URI를 확인한다.
3. `python manage.py check`와 migration 상태를 확인한다.
4. SQLite 격리 환경에서 전체 단위·통합 테스트를 실행한다.
5. Selenium 실행 환경을 준비하고 브라우저 흐름을 확인한다.
6. 일반 회원가입과 카카오 로그인을 각각 시연한다.
7. 솔로 미션 생성, 운동 기록, 배지 지급을 확인한다.
8. 두 개 이상의 계정으로 친구·파티·그룹 미션을 확인한다.
9. 랭킹에서 실제 데이터와 데모 데이터를 구분한다.
10. 배틀 데이터 생성과 접근 권한을 확인한다.
